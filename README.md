# Orbit Wars — PPO Agent

A reinforcement-learning agent for [Orbit Wars](https://github.com/Parth-D3/Space-Gladiators-Orbit-Wars),
trained with **Proximal Policy Optimization** (PPO; Schulman et al. 2017,
[arXiv:1707.06347](https://arxiv.org/abs/1707.06347)) against the repo's
example *nearest-planet-sniper* agent as the default opponent.

Everything here is built on the rules in the repo's `README.md` and `agents.md`
and on the real `kaggle_environments` `orbit_wars` environment
(`pip install "kaggle-environments>=1.28.0"`).

## Files

| File | Purpose |
|------|---------|
| `main.py` | Kaggle submission entry point. Greedy **numpy** inference of the trained policy (no torch needed). Falls back to the sniper heuristic if weights are missing. |
| `ow_features.py` | Shared code: observation encoding, action decoding, reward helper, and the pure-numpy policy. Imported by both training and submission. |
| `train_ppo.py` | The PPO trainer (PyTorch). Trains vs `sniper.py`, checkpoints every update, and exports numpy weights for `main.py`. |
| `sniper.py` | The repo's example agent (`main(1).py`), used as the training opponent. |
| `ppo_weights.npz` | Exported policy weights consumed by `main.py` (regenerated by training). |
| `ppo_orbitwars.pt` | PyTorch checkpoint for resuming training. |

## Quick start

```bash
pip install "kaggle-environments>=1.28.0" torch numpy

# 1. Train (the important step — see "Honest status" below).
python train_ppo.py --total-steps 2000000 --players mix --opponent sniper.py

# 2. Evaluate the exported weights with greedy (deterministic) play.
python train_ppo.py --eval 50 --opponent sniper.py

# 3. Test the submission exactly how Kaggle runs it.
python -c "
from kaggle_environments import make
env = make('orbit_wars', debug=True)
env.run(['main.py', 'sniper.py'])
print([(i, s.reward) for i, s in enumerate(env.steps[-1])])
"
```

## How it works

**State → action.** Each turn the policy makes one structured decision:

```
source planet  (masked to planets you own with >= 1 ship)
× target planet (masked to existing planets; your own planets => reinforce)
× garrison fraction  { no-op, 25%, 50%, 75%, send-all-but-one }
```

The decoder (`ow_features.decode_action`) turns that into the game's
`[from_planet_id, angle_radians, num_ships]` move format. It also:
- **leads orbiting targets** — iterates flight-time vs the predicted future
  position using the orbital rotation rule from the README, so fleets aim
  where the planet *will be*;
- **skips sun-crossing launches** — the README says fleets that cross the sun
  are destroyed, so those moves are dropped;
- **leaves a 1-ship defensive garrison** on the send-all action to reduce
  self-elimination.

**Network.** A per-planet MLP encoder, mean+max pooling into a global context
(plus 13 global features), and four heads: source logits, target logits,
fraction logits, and a value head. ~82k parameters. Layer names/shapes in the
torch model (`train_ppo.TorchPolicy`) deliberately match the numpy model
(`ow_features.NumpyPolicy`) so the submission reproduces the trained policy
**exactly** (verified: 0 action mismatches over 120 steps).

**Reward** (from observations, `ow_features.totals`):
- per step: `Δ(my_total_ships − best_opponent_total_ships) / 200`
- terminal: `+3` win / `−3` loss / `0` draw
  (README scoring: most total ships on planets + fleets wins; elimination also
  ends the game).

**Algorithm.** Standard PPO: clipped surrogate objective, GAE
([arXiv:1506.02438](https://arxiv.org/abs/1506.02438)), value-function loss,
entropy bonus, gradient clipping. Seats are randomized each episode so the
policy sees both player IDs.

## v2 changes (aiming, motion features, 4-player)

Driven by observed weaknesses in real Kaggle games:

1. **Intercept solver rewritten.** The old fixed-point lead calculation failed
   whenever the target's tangential speed (up to ~2.4 u/turn) rivaled the
   fleet's speed — measured ~70% misses for 10-ship fleets vs far orbiting
   planets. The new solver time-scans for the first feasible arrival turn and
   bisects for sub-turn precision, and accounts for the env's actual spawn
   point (planet center + radius + 0.1, read from the env source). Measured
   after the fix: 0 true aiming misses across moving/static source/target
   combinations (remaining non-hits are intermediate-planet collisions or
   correctly refused sun-crossing shots).
2. **Sun check extended for moving targets** — 30 units past the aim point,
   because a near-miss keeps flying and can die in the sun behind the target.
3. **Comet leading** — comet future positions are read from the observation's
   `paths`/`path_index` (position t turns ahead = `path[idx + t]`); launches
   at comets that would expire before arrival are skipped.
4. **Velocity features** — each planet's (vx, vy) is now encoded (tangential
   velocity for orbiting planets, path delta for comets, zero for static), so
   the policy can SEE motion instead of inferring it. PLANET_F is now 17:
   **old weight files are incompatible — retrain.**
5. **4-player training** — `--players {2,4,mix}` (default mix) trains 1v1 and
   1v3 episodes; eval reports per-game player count.
6. **Auto-defend (optional)** — if an owned planet's garrison drops below 10,
   the richest owned planet (holding >= 40) tops it up; disable with
   `--no-auto-defend`. Active in training and in main.py so the policy learns
   around it.

## v3 changes (anti-freeze, never-miss lanes)

1. **Big-stack freeze fixed** (planets stopped firing above ~50-300 ships):
   * the linear ships feature saturated at 200 (a 250 and a 3000 stack looked
     identical, and big stacks are rare in training -> out-of-distribution
     no-ops). Now clips at 500, with the log feature covering the rest.
   * greedy argmax is deterministic, so one blocked launch (sun lane, occupied
     lane) silently repeated forever. `greedy_moves` now does ACTION REPAIR:
     it walks the policy's own ranking (top sources x targets x fractions)
     until a launch decodes. A deliberate no-op (fraction 0) is still respected.
   * `overflow_attack` valve: any garrison above `--overflow-cap` (default 300)
     MUST attack — targets ordered flippable-first, then smallest garrison,
     static before moving. Active in training and submission.
   Regression test: full 500-turn game, longest silent streak while holding a
   300+ stack: 0 turns.
2. **Lane clearance** — every launch (policy, heuristic, defend, overflow) now
   checks the flight path against ALL other planets: static blockers by exact
   segment distance, moving blockers sampledevery half-turn against their
   predicted positions. Fleets no longer crash into intermediate planets;
   blocked lanes trigger repair to the next-best target instead of a no-op.
   (Best-effort caveat: an enemy capture or newly spawned comet can still
   wander into a lane mid-flight — no agent can prevent that.)

## v4 architecture (bigger network)

Each block gained 2 layers, and every hidden layer is old-width + 32
(uniform within a block): planet encoder & heads 64 -> 96 wide (2 -> 4
linears each), context block 128 -> 160 wide (2 -> 4 linears).
Total parameters: 81,736 -> 295,432 (~3.6x). The numpy inference side is now
depth-agnostic (it discovers each block's layers from the weight file), so
torch-side architecture changes can no longer desync the submission.
Inference cost: ~8 ms/turn — far inside the 1 s act timeout.
**Old weight files are incompatible — retrain from scratch (no --resume of
v3 checkpoints).**

## Honest status (what I verified vs. what you must do)

This was developed and tested in a sandbox with a **CPU and a wall-clock limit**,
so the shipped `ppo_weights.npz` is **under-trained**. Concretely:

- ✅ The environment, training loop, parity, and submission path all work
  end-to-end (no errors; `main.py` plays as a Kaggle file agent).
- ✅ PPO **is learning**: stochastic training winrate vs the sniper reached
  ~**64%** within 30k steps.
- ⚠️ The **greedy** (deterministic) policy that `main.py` actually submits is
  still weak (**~6–21%** vs the sniper in the runs I did). Two reasons:
  1. **Under-training.** I could only run ~30–80k steps. PPO on this game
     realistically wants **1–5M+ steps**. Throughput was ~110 steps/s on CPU;
     it will be far faster on a GPU.
  2. The sniper out-*expands* the early policy. The defensive garrison fix
     stopped most 0-ship eliminations (losses now usually end with the agent
     alive but behind on total ships), but it needs more training to learn to
     expand aggressively enough.

**Bottom line:** run `train_ppo.py` for a lot longer on your own hardware before
submitting. Watch `winrate(last50)` and `ep_ret` climb; when greedy `--eval`
winrate is consistently high, submit. The code is ready; it just needs compute.

Ideas if you want a stronger agent: more steps; self-play / league training
(periodically snapshot the policy and add it to the opponent pool); a finer
fraction grid or a continuous angle head; reward shaping for planets/production
captured.
